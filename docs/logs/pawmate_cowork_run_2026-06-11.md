### 定期契約フローβ版 — プロダクト仕様書 v1.0

#### 1. 目的

週次・月次でペットケアを依頼する飼い主に「都度予約の手間なく継続利用できる仕組み」を提供する。β版では少数の飼い主・ケアラーで動作検証し、課題を洗い出す。

#### 2. スコープ（β版 vs 本格版）

| 機能 | β版（P2） | 本格版（P3-010） |
|---|---|---|
| 申込フロー | 画面あり（簡易） | 正式 UI |
| 周期 | 週次のみ | 週次・隔週・月次 |
| 対応サービス | 散歩・訪問ケアのみ | 全サービス |
| 決済タイミング | 毎週月曜自動 | 柔軟設定 |
| キャンセル | 72時間前まで1回無料 | 詳細ルール |
| 変更 | 一時停止のみ | 柔軟変更 |
| 対象ユーザー | **招待制・限定5〜10名**（確定） | 全ユーザー |

#### 3. 定期契約の構造

```
定期契約（RegularContract）
  ├ 飼い主 ID
  ├ ケアラー ID
  ├ サービス種別（散歩 / 訪問ケア）
  ├ 曜日 × 時間帯（例: 毎週月水金 09:00〜10:00）
  ├ 開始日
  ├ 終了日（null = 無期限）
  ├ 1回あたり料金
  ├ ステータス（active / paused / cancelled）
  └ 予約インスタンス[]（各週の具体予約）
```

#### 4. データモデル

```ts
regularContract: {
  id: string;
  ownerId: string;
  caregiverId: string;
  serviceType: 'walk' | 'visit';
  schedule: {
    dayOfWeek: number[];        // 0=日〜6=土
    startTime: string;          // "HH:MM"
    durationMinutes: number;
  };
  startDate: string;            // ISO8601
  endDate: string | null;
  pricePerSession: number;      // 円
  status: 'active' | 'paused' | 'cancelled';
  pausedUntil: string | null;   // 一時停止期限
  createdAt: string;
}
```

#### 5. フロー詳細

**申込フロー（飼い主）**
```
ケアラープロフィール
  → [定期利用を申し込む] ボタン（Meet & Greet 完了済みのケアラーのみ表示）
  → サービス選択（散歩 / 訪問ケア）
  → 曜日・時間帯選択（ケアラーの空き状況と照合）
  → 開始日選択
  → 料金確認（1回あたり × 月間目安回数）
  → 規約確認・申込送信

ケアラー
  → 通知受信（24時間以内に承諾/辞退）
  → 承諾 → 定期契約 active へ

飼い主
  → 確定通知 → マイページに「定期利用中」表示
```

**決済フロー（β版）**
- 毎週月曜 AM7:00 に当週分を Stripe で自動引き落とし
- ケアラーへの分配は取引完了（ケアラーが完了報告後）に実行
- 失敗時: 飼い主に再試行通知、3回失敗で一時停止

**キャンセル・変更ルール（β版）**

| 操作 | 条件 | 手数料 |
|---|---|---|
| セッション単発キャンセル | 72時間前まで | なし |
| セッション単発キャンセル（72時間以内）| 当日含む | 料金の50% |
| 定期契約の一時停止 | 次回セッション72時間前まで | なし |
| 定期契約の解約 | 次回請求の7日前まで | なし |
| ケアラー側キャンセル | 24時間前まで | なし（代替ケアラー提案） |

#### 6. β版の検証ポイント

A07・A09 が追跡する指標:
- β利用者の継続率（4週間後の契約 active 率）
- 飼い主の平均月間予約回数（定期 vs 都度）
- キャンセル率とキャンセル理由の分布
- ケアラーのスケジュール管理上の不満（A14にフィードバック）
- 支払い失敗率（決済設計の改善判断）

#### 7. ガードレール

- β版の申込は「Meet & Greet 完了済み」ケアラーとのみ可
- 「月額固定」という表現は避ける（実際は回数 × 単価の合計請求）
- 「解約不可」「違約金あり」の印象を与える文言は使わない
- β期間中は運営側でモニタリングし、問題が起きれば手動介入できる体制を維持

#### 8. Acceptance Criteria

- [ ] 飼い主が週次定期利用を申し込める
- [ ] ケアラーが定期申込を承諾/辞退できる
- [ ] 毎週自動決済が走る（テスト環境で確認）
- [ ] 飼い主が定期契約を一時停止・解約できる
- [ ] β版として限定ユーザーのみに開放できる（フラグ管理）

### キャットシッター専門スキル プロダクト仕様書 v1.0

#### 1. 目的

猫飼い主が「猫のケアに慣れているケアラー」を見つけやすくする。犬中心のプラットフォームにならないよう、猫需要を独立したサービスラインとして可視化する。

#### 2. 追加するプロフィール項目

```ts
catCareSkills: {
  enabled: boolean;                 // 猫対応可否フラグ
  experienceYears: number | null;   // 猫ケア経験年数
  specialties: CatSpecialty[];      // 得意領域
  handledBreeds: string[];          // 対応経験のある猫種（任意）
  notes: string;                    // 自由記述（例: シニア猫の投薬対応経験あり）
}

type CatSpecialty =
  | 'indoor_only'       // 完全室内猫
  | 'senior_cat'        // シニア猫
  | 'medication'        // 投薬対応
  | 'multi_cat'         // 多頭飼い
  | 'shy_cat'           // 怖がりな猫
  | 'kitten'            // 子猫
```

#### 3. 表示位置・UI

```
  🐱 猫対応可  |  🐶 犬対応可
```

**検索・フィルタ**

- デフォルトはフィルタなし（犬・猫両方表示）

#### 4. ケアラー登録フォームへの追加

### レビュー・評価システム プロダクト仕様書 v1.0

#### 1. 目的

取引完了後に飼い主がケアラーを評価できる仕組みを作り、信頼形成と品質向上のループを回す。評価データはリピート率と並んでプロフィールの中核的な信頼指標となる。

#### 2. 評価の構造

```ts
review: {
  id: string;
  caregiverId: string;
  ownerId: string;            // 表示はハッシュ化 or 匿名
  bookingId: string;          // 紐づく取引
  overallRating: 1 | 2 | 3 | 4 | 5;
  categories: {
    reliability: 1 | 2 | 3 | 4 | 5;    // 時間通り・連絡がとれる
    petCare: 1 | 2 | 3 | 4 | 5;        // ペットケアの質
    communication: 1 | 2 | 3 | 4 | 5;  // 報告・写真の丁寧さ
  };
  comment: string;            // 自由記述（最大500文字）
  ownerName: string;          // 表示名（例: Aさん）
  petName: string | null;     // ペット名（任意）
  serviceType: string;        // 散歩 / 訪問 / 預かり等
  status: 'published' | 'pending_review' | 'hidden';
  createdAt: string;
  flaggedReason: string | null;  // 不適切フラグ理由
}
```

#### 3. レビュー投稿フロー

```
取引完了（ケアラーが完了報告）
  → 24時間後: 飼い主へレビュー依頼プッシュ通知
  → 飼い主がレビュー画面を開く
  → 総合評価（星1〜5）を選択
  → カテゴリ別評価（信頼性・ケア品質・コミュニケーション）
  → コメント入力（任意、500文字以内）
  → 送信

システム
  → 自動スクリーニング（禁止ワードチェック）
  → クリアなら即 published
  → フラグあり → pending_review（A07・A12 確認後に判断）
  → 公開されたレビューがケアラープロフィールに反映
```

#### 4. 表示仕様

**ケアラー詳細プロフィール — レビューセクション**
```
評価  ★4.8  （28件）
  信頼性     ★4.9
  ケア品質   ★4.7
  報告丁寧さ ★4.8

レビュー一覧（新しい順）
  Aさん / 柴犬 / 散歩
  ★★★★★
  「毎週お願いしています。犬が帰宅後とても満足そうで…」
  2026-09-15
  ...（最大5件表示 / 「すべて見る」で全件）
```

**集計ルール**
- 総合評価は `overallRating` の算術平均（小数点1位）
- カテゴリ別も同様
- `status: published` のみ集計に含める
- 最低3件以上のレビューがある場合のみ星評価を表示（3件未満は「レビューなし」）

#### 5. 不適切レビュー対応フロー

```
フラグ検出（自動 or ケアラーからの報告）
  → status: pending_review に変更
  → A07（Operations）が内容確認（24時間以内）
  → 問題なし: published に戻す
  → 不適切確定: hidden に変更 + 飼い主に通知
  → 判断に迷う場合: A12（Risk Review）へエスカレーション
```

不適切の基準:
- 個人を特定できる情報（住所・電話番号）が含まれる
- 根拠のない誹謗・差別的表現
- 取引と無関係の内容
- スパム・宣伝

ケアラーからの反論:
- 「返信コメント」機能で1回のみ返信可（フェーズ2後半で実装）
- 削除要求はA07経由で審査

#### 6. ケアラーへのインセンティブ

- 5件以上レビューがありかつ平均4.5以上: プロフィールに「高評価ケアラー」バッジ表示
- バッジ基準はA14（Caregiver Community）と連携してフェーズ2後半に調整

#### 7. ガードレール

- 「完全公正なレビュー」「信頼できる評価システム」の断定は避ける
- レビュー件数が少ない（< 3件）場合は星評価を表示しない
- ケアラーが自分でレビューを削除できる機能は付けない
- A12 レビュー: 名誉毀損リスクのある pending_review 案件は必ずA12を通す

#### 8. Acceptance Criteria

- [ ] 取引完了後に飼い主がレビュー・星評価を投稿できる
- [ ] ケアラープロフィールに評価サマリーとレビュー一覧が表示される
- [ ] 禁止ワードを含むレビューが自動で pending_review になる
- [ ] A07 が管理画面から pending_review のレビューを審査・公開/非公開にできる
- [ ] 3件未満のケアラーに星評価が表示されない
